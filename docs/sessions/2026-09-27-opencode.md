## Design decisions

No ADR: the ticket map marks T7 "none (omission rationale recorded here)". The
`WriteTimeout` omission rationale lives in the `ServerConfig` doc comment, the
`configs/example.yaml` field docs, and the bundle spec — no new architecture
decision beyond the existing nil-means-omitted convention (ADR-0011 d10) and the
reload non-reloadable-field rule (ADR-0015 d4).

- **`server:` is nested with one pointer field**, mirroring `ReloadConfig`, so
  the shape can grow without a flat top-level key and `Validate` can tell "key
  omitted" (nil) from "key present but non-positive". `normalizeDuration`
  defaults and rejects, so the error names the field (`server read_timeout`).
- **Only the client-facing server gets `ReadTimeout`.** The metrics and
  health-endpoint listeners keep their `ReadHeaderTimeout`; the ticket scopes the
  bound to client traffic.
- **`NonBackendChanges` gains `server` after `reload`**, so a reload that changes
  the bound is rejected whole naming the field, matching the `reload` precedent.
- **Test fixture configs must materialize the new default.** The chaos builders
  construct `config.Config` directly (only some call `Validate`), so each gains
  `Server: config.ServerConfig{ReadTimeout: &readTimeout}`; without it the
  unvalidated reload config panicked in `NonBackendChanges`.

## Known finding from review (spec premise corrected, not propagated)

The spec and ticket claim idle keep-alives "remain bounded by the standard
library's fallback chain (`IdleTimeout` → `ReadTimeout` → `ReadHeaderTimeout`),
which resolves to 5s today". That is factually wrong: `net/http`'s
`idleTimeout()` is `IdleTimeout` else `ReadTimeout` only — `ReadHeaderTimeout` is
not in the chain. So wiring `ReadTimeout = 60s` bounds idle keep-alives at 60s
where they were previously unbounded (both fields were zero). This still delivers
story 8 (idle connections are bounded) and is an improvement, but at a different
value than the spec states. Documented honestly in `ServerConfig.ReadTimeout`
and `configs/example.yaml` rather than restating the wrong 5s claim.

The slow-loris test drives a raw TCP client that declares a 10 MB body, sends two
bytes, and stalls, against a backend that drains the body before answering (so no
response can arrive until the full body does). The connection is cut off well
under the test's own 3s deadline; the observed response is 499 (`client_canceled`)
or 502. Without the wiring the client would hang to the test deadline and the
`elapsed < 2s` assertion would fail — the test has teeth.
