## Decisions

- **The rate's peak is resolved with the backends fast.** When `degraded` runs
  alone it discovers the h2/round-robin/10 KiB LB peak *before* injecting the
  50 ms delay, so the rate is the same normal peak the core slice would have
  measured and the eight runs stay comparable to core. Reuse is by a variable
  set in `run_core`, not by reading `results/core/…` — that file survives
  across invocations, and the ticket says the rate comes from the *same
  invocation's* core result, so a standalone `degraded` run must self-discover.
- **Every degraded run is bracketed, but only consistent-hash gets a hot-key
  line.** The spec asks for the per-backend distribution on all eight and the
  owner/spill on consistent-hash, so `measured_attack` gained a `hotkey` flag
  rather than a second bracket function; the core slice's three non-consistent
  algorithms are unchanged (empty scheme, no reads).
- **Restore is an EXIT trap that chains the provenance finalizer.**
  `provenance_start` already owns the single EXIT trap; `run_degraded` replaces
  it with `restore_degraded; provenance_finish`, so an abort anywhere in the
  slice still drops backend3 to 0 and still writes the record. `restore_degraded`
  is idempotent via the flag.
- **One compose anchor change, no per-service override.** `SLEEP_MS` is exported
  and only backend3 is force-recreated while it is 50; compose leaves the other
  three running at 0. This is the same exported-variable pattern as `LB_CONFIG`,
  `NGINX_CONF`, and `BACKEND_TLS_*`.
- **No Go, no backend, no Nginx, no config change.**
