## Done

- `bench/run.sh` gains a `smoke` slice. `run_smoke` calls `smoke_proto` once
  per protocol: it brings the backends and nginx up, then for each algorithm
  recreates the LB on `./configs/<proto>/<algo>.yaml` and nginx on
  `nginx_conf_for <proto> <algo>`, and runs `smoke_attack` for `lb` and
  `nginx`. That is 4×2 + 1×2 = 10 attacks.
- Smoke parameters are constants beside the others: `SMOKE_RATE=50`,
  `SMOKE_SECS=2`, `SMOKE_SIZE=10kb`, `SMOKE_READY_TRIES=5`.
- `smoke_attack` refuses anything below 100% 200s. vegeta's `success` field
  counts 3xx as success, so `smoke_ok_200` counts the report's `"200"` entries
  against `requests`; a redirect is a routing bug and fails the gate.
  `wait_target` polls one request up to `SMOKE_READY_TRIES` first, so a
  container still starting is not misread as a broken route. A failed
  combination is named (`smoke FAILED: <proto>/<algo>/<comp> — …`) and the
  slice exits nonzero after running all ten.
- `smoke` is **not** part of `all`. The header comment, `usage()` text and
  `bench/README.md` (layout bullet and a new Running paragraph) list it
  separately.

## Decisions

- No ADR. The bundle spec's "Decisions explicitly not taken" covers this unit;
  nothing here is hard to reverse, surprising and a real trade-off.
- The gate checks 200s specifically rather than vegeta's `success`, because
  `success` includes 3xx and the ticket's intent is "serves 200s".
- `wait_target` readiness polling is a small addition beyond the ticket text; it
  exists so container startup time is not the failure the gate reports. Its
  retry count is a constant, like every other harness parameter.
- `smoke_proto` taking the algorithm list lets both protocol loops share one
  code path; `smoke` therefore auto-covers any algorithm later added to `ALGOS`.
