## Design decisions

- **Counter placement.** `requests atomic.Int64` on `flippableBackend`, the
  harness's single backend type. `atomic.Int64` matches the ADR-0010 precedent
  (EWMA latency is an `atomic.Int64`); a counter needs no mutex.
- **Increment point.** `serve()` — the one dispatch point every request
  flows through before the installed handler runs, hence before any gating in
  `ServeGated`. One increment covers every handler class (200/500/gated) and
  health probes; no existing handler changes, which is what the additive
  requirement demands. Increment-before-gate is what lets a later test assert
  a removed backend's count froze while its requests were still held.
- **Readability.** `RequestCount() int64` accessor; the test drives real HTTP
  at `fb.URL()` and never assembles the app, so it touches no proxy or registry
  internals.
- **No ADR.** No architectural decision beyond existing harness/atomic
  patterns; recorded here per AGENTS.md Step 2.
