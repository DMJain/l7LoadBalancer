## Design decisions

ADR-0015 already records the reload architecture, including the added-backend
admission rule (decision 10) and removed-backend observer suppression (decision
8), so no new ADR was needed for this ticket (the bundle's ticket map marks it
"covered by ADR-0015").

Two implementation choices were made and documented in code:

1. **`Remove` waits for the prober goroutine to exit.** `probeOnce` checks
   `ctx.Err()` after `probe` returns and before applying any outcome, which
   stops a cancelled probe from marking, logging, or writing a gauge. `Remove`
   additionally cancels and then waits on a per-prober `done` channel, so once
   it returns, no outcome can be applied afterwards — making S4.T3's subsequent
   series deletion deterministic and race-free. The handle struct is still, as
   the ticket requires, a cancel function in a mutex-guarded map, plus that
   exit signal.
2. **`Add(ctx, b)` is the reload API and always means "added".** The shared
   unexported `add(ctx, b, added)` backs both `Add` and `Start`, so startup
   probers keep their original admission rule (start healthy, two-success
   recovery, first probe after one interval) while reload-added probers start
   unhealthy, probe immediately, and are admitted by one success. Keeping the
   mode out of the public signature avoids a bare `added bool` at the one
   production call site; `Start` is the only non-added caller.

## Design decisions

ADR-0015 already records the reload architecture, including the non-backend
reject rule (decision 4), removed-backend observer suppression (decision 8),
pull-based ring rebuild (decision 9), added-backend admission (decision 10), the
blue/green WARN (decision 11), and diffing against the loaded record (decision
12), so no new ADR was needed ("covered by ADR-0015"). Implementation choices
made here:

1. **`App.Reload` logs its own outcomes; the loop logs only what it detects.**
   `Reload` has the application logger and owns the non-backend rejection and
   the success line, so those logs sit next to the detection; `main`'s loop logs
   only parse and validation failures, which it alone detects. Both use the
   frozen `logger` constants, so no call site invents a string and a loop test
   with one captured logger sees every reload line regardless of origin.
2. **Removals before additions in the hook-up.** A same-name re-added identity
   (blue/green, or a re-add under a new URL) would otherwise have its freshly
   seeded series deleted by the removal pass. Removals first also means
   `checker.Remove` has returned before the fresh backend is probed, so the old
   prober cannot write the gauge afterwards. Added series are seeded before
   `checker.Add`, so a first successful probe cannot race the `healthy 0` seed.
3. **`config_reload_failed` reasons are a closed set.** `reason` is one of
   `parse_error`, `validation_error`, `non_backend_change`, or the defensive
   `apply_error` (unreachable for production callers, since `Validate` rules
   out the diffs `Apply` rejects); the changed field names ride a separate
   `fields` attribute rather than being shoved into `reason`, keeping the
   `reason` vocabulary closed and grep-able (story 59).
4. **Burst collapse via a pre-reload drain.** The loop drains every queued
   signal before doing anything, so N pending SIGHUPs are one reload. With the
   production buffer of 1 a reload in progress can leave at most one more
   signal buffered, so reloads never overlap or pile up (ADR-0015 decision 1).

claim commit) — Standards and Spec axes.

- **Spec found one real bug.** `Registry.Apply` published the new snapshot with
  reload-added backends still healthy (`newBackend` calls `MarkHealthy`), and
  only `checker.Add` — which runs after `Apply`, the removal loop, and the
  seeding loop — marked them unhealthy. Any request selected in that window was
  routed to an unproven URL, contradicting story 6 / ADR-0015 decision 10. Fixed
  at the swap point: `Registry.Apply` now calls `MarkUnhealthy` on each freshly

  never in the selectable set until its first successful probe. This closes
  T2's documented hand-off ("T3 changes added backends to start unhealthy");
  startup backends still start healthy via `NewRegistry`. `Registry` tests now
  pin added-instances-unhealthy. The Spec agent also noted `ReasonApplyError` as
  a fourth reason beyond the spec's three — kept deliberately (Apply can error,
  and the alternative is a failure line with no reason), recorded in the
  vocabulary comment.
- **Standards: no hard violations.** Addressed: `logger/doc.go` now lists the
  reload-scoped canonical fields (`event`, `reason`, `added`, `removed`,
  `unchanged`, `fields`); the reload success line uses one `a.log.Log` call
  instead of a Warn/Info branch; the loop's ignored `Reload` error is explicit
  (`_ = application.Reload(...)` with a comment) rather than an empty-bodied

  registry apply succeeds" to match the ticket's ordering. Noted but not
