## Design decisions

ADR-0015 already records the reload architecture, including the added-backend
admission rule (decision 10) and removed-backend observer suppression (decision
8), so no new ADR was needed for this ticket (the bundle's ticket map marks it
"covered by ADR-0015").

Two implementation choices were made and documented in code:

1. **`Remove` waits for the prober goroutine to exit.** `probeOnce` checks
   `ctx.Err()` after `probe` returns and before applying any outcome, which
   stops a cancelled probe from marking, logging, or writing a gauge. `Remove`
   additionally cancels and then waits on a per-prober `done` channel, so once
   it returns, no outcome can be applied afterwards — making S4.T3's subsequent
   series deletion deterministic and race-free. The handle struct is still, as
   the ticket requires, a cancel function in a mutex-guarded map, plus that
   exit signal.
2. **`Add(ctx, b)` is the reload API and always means "added".** The shared
   unexported `add(ctx, b, added)` backs both `Add` and `Start`, so startup
   probers keep their original admission rule (start healthy, two-success
   recovery, first probe after one interval) while reload-added probers start
   unhealthy, probe immediately, and are admitted by one success. Keeping the
   mode out of the public signature avoids a bare `added bool` at the one
   production call site; `Start` is the only non-added caller.

## Design decisions

ADR-0015 already records the reload architecture, including the non-backend
reject rule (decision 4), removed-backend observer suppression (decision 8),
pull-based ring rebuild (decision 9), added-backend admission (decision 10), the
blue/green WARN (decision 11), and diffing against the loaded record (decision
12), so no new ADR was needed ("covered by ADR-0015"). Implementation choices
made here:

1. **`App.Reload` logs its own outcomes; the loop logs only what it detects.**
   `Reload` has the application logger and owns the non-backend rejection and
   the success line, so those logs sit next to the detection; `main`'s loop logs
   only parse and validation failures, which it alone detects. Both use the
   frozen `logger` constants, so no call site invents a string and a loop test
   with one captured logger sees every reload line regardless of origin.
2. **Removals before additions in the hook-up.** A same-name re-added identity
   (blue/green, or a re-add under a new URL) would otherwise have its freshly
   seeded series deleted by the removal pass. Removals first also means
   `checker.Remove` has returned before the fresh backend is probed, so the old
   prober cannot write the gauge afterwards. Added series are seeded before
   `checker.Add`, so a first successful probe cannot race the `healthy 0` seed.
3. **`config_reload_failed` reasons are a closed set.** `reason` is one of
   `parse_error`, `validation_error`, `non_backend_change`, or the defensive
   `apply_error` (unreachable for production callers, since `Validate` rules
   out the diffs `Apply` rejects); the changed field names ride a separate
   `fields` attribute rather than being shoved into `reason`, keeping the
   `reason` vocabulary closed and grep-able (story 59).
4. **Burst collapse via a pre-reload drain.** The loop drains every queued
   signal before doing anything, so N pending SIGHUPs are one reload. With the
   production buffer of 1 a reload in progress can leave at most one more
   signal buffered, so reloads never overlap or pile up (ADR-0015 decision 1).

## Design decisions

ADR-0016 was written and committed before any code (`245eee7`) and records all
of them: the pointer-duration `reload.drain_window` (default 30s, non-reloadable
and named by `NonBackendChanges`); the per-backend retired context with
`ErrDrainWindowExpired` as its cause and the nil-tolerance that keeps
zero-value fixtures working; the `context.AfterFunc` join (rejected: a
goroutine per request, a mutex-guarded cancel-func registry, and a
channel-select around the round trip); before-headers 502 vs after-headers
truncation; and the drain mechanism T4 will add (two-phase poll, shutdown
abandonment, independence from later reloads). `AGENTS.md` gained the ADR row
and key-decision 23.

One implementation detail worth recording: the proxy's join is two deferred
calls in `ServeHTTP` (`stopRetire` then `cancel(nil)`, in LIFO order) rather
than state on `reqState`. `ReverseProxy` copies the response body
synchronously, so `ServeHTTP` returning *is* request completion; the
`AfterFunc` stop is what prevents a long-lived backend accumulating one dead
callback per completed request, and the cancel releases the derived context.
The error handler attributes the WARN line by comparing
`context.Cause(r.Context())` against `backend.ErrDrainWindowExpired`, so a
client cancellation (`context.Canceled`) and a transport failure are untouched.

## Design decisions

No new ADR: ADR-0016 (accepted in T4.0) fixes the contract this ticket
implements. The remaining choices are code comments, not ADR-bar decisions:

- **Two-phase poll in one synchronous method.** `drainBackend` blocks (phase
  one: `ActiveConns` zero within the window; phase two: after `Retire`, wait
  for zero) and `Reload` starts it with `go`. Making it synchronous is what
  lets the shutdown test drive it directly.
- **`waitActiveZero(ctx, b, timeout)`**: `timeout == 0` means no deadline
  (phase two), implemented by a nil `timeoutCh` so the select arm disables.
  `time.NewTimer` (not `time.After`) so an early ctx/idle return stops it.
- **Shutdown returns without cleanup.** Both waits select on `ctx.Done()`; the
  caller returns before `completeDrain`, so no log and no series deletion — the
  literal ADR-0016 decision 8 semantics ("the process is ending").
- **`cancelled` read before `Retire`**: the active count at window expiry is
  the set that gets cancelled. `context.AfterFunc` runs its callbacks in their
  own goroutines, so reading after `Retire` would race the unwinding requests.
- **Log levels** (unspecified by the issue): `window_expired` at WARN (requests
  were cut off), `idle` at INFO. Recorded in the contracts doc example.
- **Name-in-use check reads `reg.All()`** after `Apply` has published the new
  snapshot, so a same-name fresh backend's series is never deleted, regardless
  of whether its seeding has run yet.

## Design decisions

- **`clientCtx` captured before the drain join.** `ServeHTTP` stores
  `r.Context()` in `reqState` before deriving the cancel-with-cause context, so
  the error handler can ask "did the *client* cancel?" without seeing the drain
  cause. Concurrency follows ADR-0007: request-goroutine-only, no lock.
- **Predicate order is the design** (spec story 22). Drain cause first (most
  specific, already proven by ADR-0016), then `clientCtx.Err() != nil`, then the
  transport-failure fallback. A transport timer (dial, response-header) never
  cancels the client's request context, so a real backend timeout falls through
  to tier 3 and is still recorded as a failure. Cancellation is sticky, so
  checking at error-handler time is race-free.
- **`statusClientClosedRequest = 499`** (nginx's client-closed-request code).
  Written to the recorder, metrics (`status_class="4xx"`), and logs only; the
  wire write to a dead client is a no-op. The 5xx class stays reserved for
  backend-caused failures.
- **Client-gone does not call `observe`** — not even the removed-backend
  suppression check — because no round trip completed. It still calls
  `release()` (once-guarded) so the slot drains.
- **INFO, not WARN, for the client-gone cause line.** It is not a failure, so
  it must not read as one; the drain path keeps its WARN `window_expired` line.
- **No ADR** — the ticket map records the predicate for later ADRs, and T5 adds
  no new subsystem.
