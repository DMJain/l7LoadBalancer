## Design decisions

ADR-0015 already records the reload architecture, including the added-backend
admission rule (decision 10) and removed-backend observer suppression (decision
8), so no new ADR was needed for this ticket (the bundle's ticket map marks it
"covered by ADR-0015").

Two implementation choices were made and documented in code:

1. **`Remove` waits for the prober goroutine to exit.** `probeOnce` checks
   `ctx.Err()` after `probe` returns and before applying any outcome, which
   stops a cancelled probe from marking, logging, or writing a gauge. `Remove`
   additionally cancels and then waits on a per-prober `done` channel, so once
   it returns, no outcome can be applied afterwards — making S4.T3's subsequent
   series deletion deterministic and race-free. The handle struct is still, as
   the ticket requires, a cancel function in a mutex-guarded map, plus that
   exit signal.
2. **`Add(ctx, b)` is the reload API and always means "added".** The shared
   unexported `add(ctx, b, added)` backs both `Add` and `Start`, so startup
   probers keep their original admission rule (start healthy, two-success
   recovery, first probe after one interval) while reload-added probers start
   unhealthy, probe immediately, and are admitted by one success. Keeping the
   mode out of the public signature avoids a bare `added bool` at the one
   production call site; `Start` is the only non-added caller.

## What was built

`internal/health/checker.go`

- `Checker` gains a `sync.Mutex` and `probers map[*backend.Backend]*proberHandle`;
  `Start` delegates to the new unexported `add(ctx, b, false)`.
- `Checker.Add(ctx, b)` is the reload path: `add(ctx, b, true)` marks `b`
  unhealthy and runs an added prober.
- `Checker.Remove(b)` cancels the prober and waits for its goroutine to exit; a
  backend not being probed is a no-op.
- `probeOnce` returns early when `ctx.Err() != nil`; the success branch selects
  `probeInitialSuccessesBeforeHealthy = 1` with reason `logger.ReasonInitialProbe`
  while `prober.added` is set, then consumes the flag and resets the success
  streak so later recovery uses the normal two-success threshold.
- `prober.run` probes once immediately when `added`.

`internal/health/outlier.go`: `OutlierDetector.Forget(b)` deletes the backend's
window under the existing mutex.

`internal/metrics/metrics.go`: `Collector.DeleteBackendHealthy` and
`Collector.DeleteCircuitState` (all three state labels). Neither touches the
active-connections series, which S4.T4 deletes at drain completion.

`internal/logger/vocab.go`: new `ReasonInitialProbe = "initial_probe"`;
`EventHealthReinstated`'s doc widened to cover first admission. `vocab_test.go`
pins the value and bumps the closed-vocabulary size to 8.

`CONTEXT.md`: the **Probe** glossary entry now names the single-probe
added-backend exception.

## Hand-off (recorded per the issue)

Nothing calls `Add`/`Remove`/`Forget`/the delete methods in production yet — T3's
reload does. Because `Add` marks an added backend unhealthy itself, T3 does not
need to do so; T3 still seeds the added backend's gauge series (active
connections 0, healthy 0, circuit closed) before calling `Add`. The removed
backend's active-connections series is deliberately left in place — T4 deletes it
at drain completion. The probe-round-complete latch is never cleared by
add/remove (ADR-0014 decision 4).
