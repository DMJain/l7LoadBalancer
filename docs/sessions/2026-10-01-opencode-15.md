## Done

- `bench/run.sh`:
  - Constants `DRAIN_BACKEND=backend4`, `DRAIN_POLL_TRIES=100`,
    `DRAIN_POLL_SLEEP=0.2` with the reload constants.
  - `inode_of <file>` prints the inode (`stat -f %i` on Darwin, `stat -c %i` on
    Linux). `reload_seen_count` refreshes the LB log file and prints the
    `config_reloaded` line count, so the drain reload recognizes the moment its
    own reload is applied even though the no-op reload already logged one.
  - `snapshot_block <label> <snapshot>` emits the raw per-backend `/stats` counts
    as `# snapshot=<label> backend=<name> count=<n>` header lines.
  - `reload_verdict` gains an optional fifth argument, an extra failed-criterion
    name joined into the one `FAIL failed=…` list; the no-op call is unchanged.
  - `failure_event` gains a `drain` mode and `sighup-drain` label. Its scheduler
    sleeps to the event, captures the working copy's inode, `cp`s the derived
    config over it, asserts the inode is unchanged (aborting otherwise), takes
    snapshot 1, counts the reload lines, sends SIGHUP, polls until the count
    grows (writing `$TMP/drain-applied` when it does), and takes snapshot 2.
    After the attack, snapshot 3 is taken. The result branch computes
    snapshot 2 − snapshot 1 (`drain_before_applied_backend4`, recorded only) and
    snapshot 3 − snapshot 2 (`drain_applied_end_backend4`, judged) via the T8.1
    `arrival_deltas`, names `drain_isolation` when the second is nonzero and
    `reload_not_applied` when `config_reloaded` was never seen (so a run that
    silently failed to reload cannot pass), and writes the three
    `snapshot_block`s plus the measurements and verdict. `kill` and `sighup` are
    otherwise unchanged.
  - `run_failure` copies the committed config to
    `bench/results/.tmp/reload-config.yaml`, derives
    `bench/results/.tmp/drain-config.yaml` with `grep -v backend4`, mounts the
    working copy for both reload runs (`set_lb ./results/.tmp/reload-config.yaml`)

## Decisions

- **The working copy is mounted for both reload runs.** The spec says "for the
  reload runs"; `set_lb` the copy once before the no-op and drain runs keeps them
  grouped, and the drain's in-place rewrite is visible through the single-file
  bind mount only because the identity is stable.
- **The reload-applied signal is a line _count_, not a line.** The LB logs
  `config_reloaded` for the no-op run too, so `reload_seen_count` captures the
  count before the drain SIGHUP and waits for it to grow. A bare grep would match
  the earlier run's line and take snapshot 2 before the reload was applied.
- **Snapshot 2 is taken by the event subshell, snapshot 3 by the foreground.**
  The event fires at T+30 s while the 60 s attack still runs, so snapshot 2 must
  be concurrent with the attack; the fragment stays inside the existing
  `( … ) &` scheduler and the foreground reads its output file after `wait`.
- **One verdict line names every criterion.** `reload_verdict` takes an optional
  extra failed name rather than a second, drain-only verdict function, so the
  drain result reads exactly like the no-op one plus `drain_isolation`.
- **`exit 1` on a drain event failure, `warn` for kill/sighup.** The ticket
  requires the inode assertion to abort; the older modes keep their warn-only
  behavior.
- **No Go, no backend, no Nginx, no new committed config.**
