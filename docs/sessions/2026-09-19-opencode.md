# Session: 2026-09-19 — opencode

## Goal

S2.T1.1 (issue 01 of
`.scratch/s2-t1-t2-consistent-hash-bounded-loads/`) — the consistent-hash
ring primitive. An unexported, placement-only `ring` in `internal/balancer`
that deterministically maps a hash key to a backend via virtual nodes and
exposes an ordered candidate walk, as the shared foundation both Sprint 2
consistent-hash selectors build on. TDD per `AGENTS.md`; ADR-0008 records
the hash pipeline, vnode key order, and vnode count decisions.

## Done

- `internal/balancer/ring.go` (new):
  - Unexported `ring` / `vnode` types. No `Select`, no health awareness, no
    capacity awareness — placement only.
  - Built once by `newRing(all)` from `Registry.All()` (every backend
    regardless of health); 150 virtual nodes per backend; no rebuild API.
  - Hash pipeline `hashKey`: stdlib `hash/fnv` `New64a()` → `Sum64()` →
    `fmix64` Murmur3 finalizer, shared with later request-key hashing.
  - Virtual-node keys `<index>:<name>` (index first).
  - `candidates(key) iter.Seq[*backend.Backend]`: binary-searches the key's
    ring position and yields each distinct backend once, wrapping around.
    An `iter.Seq`, not a predicate callback, so selectors keep skip logic
    inline (ADR-0008).
  - Concurrency note: immutable after construction, safe to share
    read-only across goroutines.
- `internal/balancer/ring_test.go` (new, Red-first against undefined
  symbols):
  - Stable mapping: same key → same backend across repeated calls and
    across two identically-built rings.
  - Minimal disruption: adding a 5th backend remaps 20.75% of 10k keys
    (asserted 15–25%); removing one remaps 27.05% (asserted 22–32%).
  - Vnode uniformity: 20k random keys land within ±10% of an even 4-way
    split.
  - Distinct-once walk across 200 keys; empty ring yields nothing.
- `docs/adr/0008-consistent-hash-ring-pipeline-and-vnode-layout.md` (new):
  - Records all three decisions with reproductions of the design-session
    measurements.
- `AGENTS.md` — ADR-0008 added to the decision index + key decision #16.
- `docs/architecture.md` — ADR-0008 indexed; ring primitive noted under
  "where new selection algorithms plug in".
- `PROGRESS.md` — Sprint 2 section scoped into S2.T1.1/S2.T1.2/S2.T2;
  S2.T1.1 flipped `[IN_PROGRESS]` → `[DONE]`; session-log entry added.

## Decisions

- **ADR-0008 written in the Design step, before code**, so the hash
  pipeline / vnode key order / vnode count have a durable record independent
  of the Sprint 2 spec (which is untracked scratch).
- **Evidence independently reproduced.** The spec's three evidence claims
  were re-measured during this task rather than restated on faith. Two
  reproduce on the design fixture shape (4 URL-named backends, `index:name`,
  150 vnodes, raw FNV): a /24 subnet collapses onto 3 of 4 backends
  (90/100/0/66 of 256), and `name:index` spreads 6.1–36.2% vs `index:name`'s
  23.0–26.8%. The `fmix64` finalizer fixes the collapse (all 4 backends hit
  82/59/54/61).
- **Honest caveat recorded in ADR-0008.** The vnode key-order gap is
  measured on *raw* FNV; after the finalizer both orders are near-uniform
  (reproduction: 5.5 pts vs 3.6 pts spread). `index:name` is retained as the
  design-record choice (free, safer pre-finalizer, defense in depth) and
  ADR-0008 says so explicitly rather than overclaiming that the order is
  load-bearing post-finalizer. The spec's "independent of the finalizer"
  phrasing is imprecise; the decision itself is unaffected.
- **Test tolerances tightened from observed, fixed-seed values.** Uniformity
  was loosened from an initial ±20% to ±10% once the actual spread (~5.5%)
  was observed; disruption bounds set at 15–25% / 22–32% around observed
  20.75% / 27.05%. Fixed seeds make these deterministic, not flaky.
- **Ring API is `iter.Seq` only** — no convenience "map key → backend"
  method. The mapping is the first yielded candidate, which is what the
  tests and both selectors consume; adding a second API would be
  speculative.
- **Sprint 2 PROGRESS entries are ticket-level** (`S2.T1.1`, `S2.T1.2`,
  `S2.T2`), because the `.scratch` tickets close independently and the
  spec-level S2.T1 covers two of them. Documented in the Sprint 2 intro to
  avoid ID confusion.

## S2.T1.2 — `naiveConsistentHash` selector (issue 02)

### Goal

S2.T1.2 (issue 02 of
`.scratch/s2-t1-t2-consistent-hash-bounded-loads/`) — a real, working,
health-aware but load-blind consistent-hash `Selector` over ticket 01's ring,
deliberately unwired from config, existing as the empirical comparator the
bounded-loads ADR and hot-key test (ticket 03) measure against. TDD per
`AGENTS.md`.

### Done

- `internal/balancer/naive_consistent_hash.go` (new): unexported
  `naiveConsistentHash` holding only the immutable ring; `Select` walks
  `ring.candidates(requestHashKey(r))` and returns the first `IsHealthy()`
  candidate, else `ErrNoHealthyBackends`. Compile-time `Selector` assertion.
  Doc comment states the unwired-by-design rationale, references ADR-0008, and
  explains the deliberate non-name `ConsistentHash`.
- `internal/balancer/hashkey.go` (new): `requestHashKey(*http.Request)` — the
  `RemoteAddr` client IP with the port stripped, shared by both CH selectors
  (ticket 03 reuses it unchanged). Unparseable/empty addresses pass through
  unchanged, documented as intentionally concentrating upstream bugs on one
  backend.
- `internal/balancer/naive_consistent_hash_test.go` (new, Red-first against
  undefined symbols): stable affinity per client (repeated + two
  independently-built selectors), port-stripping at the `Select` seam,
  scripted health transition (skip → resume), key-matters teeth check (400
  octet-diverse IPs over 4 backends, each ≥10%), empty healthy set (zero
  backends and all-unhealthy), and a concurrent `-race` select test.
- `internal/balancer/hashkey_test.go` (new): direct table test of the key
  derivation (IPv4, IPv6 brackets, bare host, empty).
- `cmd/l7LoadBalancer/dce_test.go` (new): builds the production binary for a
  pinned linux/amd64 target and asserts `naiveConsistentHash` is absent, with a
  `RoundRobin` positive control so the absence check cannot be vacuous.
- `internal/balancer/ring_test.go`: `randomClientIP` → `randomIP` (one-token
  rename to the Sprint 2 spec's committed name; same explicit `*rand.Rand`
  seeding, no behavior change) so ticket 03 reuses it instead of duplicating.
- `PROGRESS.md`: S2.T1.2 `[IN_PROGRESS]` → `[DONE]`; issue 02 boxes ticked;
  this log appended.

### Decisions

- **No new ADR.** The issue says "reference ticket 01's ADR (ADR-0008)", and
  the "why bounded-loads over naive" argument plus its seed-24 evidence belong
  in one place — ADR-0009 at ticket 03. Ticket 02's own choices (health-only
  skip, `RemoteAddr` key, unwired-by-design) are recorded in ADR-0008 and the
  type's doc comment.
- **`requestHashKey` lives in its own `hashkey.go`, not in the naive file.**
  It maps to the `Hash key` term in `CONTEXT.md` and is shared with ticket 03;
  having the never-wired comparator own shared production infrastructure would
  be a naming/dependency smell.
- **Empty registry is a runtime condition, not a construction error.**
  `newNaiveConsistentHash` takes no error and `Select` returns
  `ErrNoHealthyBackends` — matching Sprint 1's selectors and the frozen
  no-error `NewConsistentHashBoundedLoads(reg)` stub. Making the constructor
  error-returning would be a silent change to a frozen contract; `config`
  already owns "zero backends is a config error".
- **Production-dead code is verified dead, not assumed.** `go tool nm` showed
  the type DCE'd from the binary (the blank `var _ Selector` assertion emits no
  itab). This was turned into the `dce_test.go` invariant rather than left as a
  remembered fact, with a comment pricing in the gc/linker brittleness.
- **Test hardening from the grilling round:** keep both port-stripping tests
  (unit vs. end-to-end seams); add the key-matters teeth test the affinity
  tests lacked; add a concurrency test to back the type's own concurrency
  claim. `randomIP` seed documented as "arbitrary, changing it re-derives
  counts but not the invariant".
