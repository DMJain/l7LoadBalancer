## Done

- `bench/run.sh`:
  - Run-count constants at the top: `CORE_RUNS` = `#ALGOS × #SIZES × 2
    competitors × {peak, latency}` = 48, `PROTOCOL_RUNS` = 12, `FAILURE_RUNS` =
    2, `SMOKE_RUNS` = 10. `run_total <slice>` sums them; `all` is 62 today.
  - `fmt_hms <seconds>` prints `HH:MM:SS`.
  - `progress <proto> <algorithm> <size> <competitor> <load-type>` prints
    `[run N/total] <scenario> <load-type>  elapsed HH:MM:SS  eta HH:MM:SS` to
    stderr and advances a counter. Before the first run the ETA is `--`; after
    it, `elapsed × total / completed` exactly as the spec states.
  - Calls before each scenario's peak-search run and latency run
    (`run_scenario`), before each failure event (`failure_event`), and before
    each smoke combination (`smoke_proto`). The `core`/`protocol` protocol
    token is `proto` with core defaulting to `h2` (the argument is empty there
    only to keep the core result filenames proto-free — spec §30).
  - `main` sets `RUN_TOTAL` from the selected slice and `RUN_START` before
    dispatch; every new write is `>&2`, so stdout is unchanged.
  - Header comment documents the progress behaviour.
- One "run" is one result set: a scenario's peak-search run (peak discovery plus
  the throughput measurement at peak) and its latency run (the whole rate
  sweep) — which is why core is 48, not 144.

## Decisions

- The total is computed from the selected slices, so it is correct at this
  point in the bundle (smoke 10, core 48, protocol 12, failure 2, `all` 62).
  S5.T8 and S5.T9 add their runs and update the same constants; hardcoding the
  spec's final 71 now would make the line lie about a run of the current
  harness (issue 09 acceptance, spec §Provenance).
- Progress is emitted at the start of each run, so `completed` in the ETA
  formula counts runs already started. This is what makes `--` appear before
  the first line and a real ETA from the second.
- No new helper abstraction beyond `fmt_hms`/`progress`/`run_total`; no ADR.
