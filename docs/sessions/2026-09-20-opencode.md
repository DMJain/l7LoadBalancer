## Decisions

- **ADR-0010 written in the Design step, before code** (AGENTS.md Step 2.8), so
  the `Backend`-owned-latency, cold-start, and failure-penalty decisions have a
  durable record independent of the untracked `.scratch` spec. The Evidence
  section was added after the test ran, carrying this task's own recorded
  numbers, the same way ADR-0009 did.
- **The measurement window is the backend round trip only, and that is a
  second timestamp.** `director()` → `modifyResponse`, not the
  `ServeHTTP`→body-close window `latency_ms` measures. Reusing `start` would
  have made a slow client look like a slow backend to P2C.
- **Failure records a flat 2s, not elapsed time.** With a fast failure
  (connection refused) the real elapsed time would be near-zero and P2C would
  treat the failing backend as the *fastest* one — a wrong-signed signal. 2s
  dominates the committed 50/150/300ms dummy latencies; the ADR notes `SLEEP_MS`
  has no enforced ceiling, so the margin is a deliberate headroom choice, not
  an assumed bound.
- **Two random indices via `rand.IntN` package functions, not a
  `*rand.Rand`.** A per-selector RNG would need its own mutex, undercutting the
  lock-free CAS-based `RecordLatency`/`EWMALatency` design. The distinct-index
  draw (`j` in `[0,n-2]`, incremented past `i`) is the standard unbiased
  two-sample-without-replacement construction.
- **Tie-breaking is arbitrary.** Unlike `LeastConnections`, two EWMA values
  derived from different floating-point histories are not a
  reproducible-by-design tie, so no registry-order rule is promised (matching
  the spec).
- **The load-skew test uses four backends, not two.** With two healthy
  backends both are always sampled, so the test degenerates to "always the
  faster" — true, but no sampling is visible. Four backends shows the real
  property: the fast backend is drawn half the time and lands ~50% of requests
  while each slow peer gets ~1/6. The two-backend deterministic case is still
  pinned separately (`...PrefersFasterOfTwo`).
- **A `t.Logf` in the load-skew test records the actual split** (one run:
  fast 2,043/4,000 = 51.1%, slow 671/647/639) so the property's numbers are
  visible under `-v` and mirrored in ADR-0010, rather than asserted only as a
  bound.

## S3.T0.2 — Round-trip observer fan-out (issue 02)

Second Sprint 3 task: a prefactor that replaces the proxy's single hardcoded
`state.backend.RecordLatency(...)` call with a generic `RoundTripObserver`
fan-out, so S3.T2 (passive outlier detection) and S3.T3 (circuit breaker) can
each register a listener with zero further changes to `proxy.go`'s hook logic.
Shape pinned by ADR-0011 decision 9; no new ADR. TDD per `AGENTS.md`.

### What was done

- `internal/proxy/proxy.go`:
  - New consumer-defined `RoundTripObserver` interface —
    `ObserveRoundTrip(b *backend.Backend, d time.Duration, success bool)` —
    with a doc comment recording the "recording is unconditional; gating is
    conditional" rule and why an early-return guard would be wrong.
  - `Proxy` gains an unexported `observers []RoundTripObserver` slice and an
    additive `RegisterObserver(o RoundTripObserver)` method; `New(reg, sel)`'s
    frozen two-argument signature is untouched. Registration is documented as
    construction-time-only (slice read on the request path without a lock).
  - New `observe(state, d, success)` helper is the single fan-out path.
  - `modifyResponse` computes `success := resp.StatusCode < 500` and
    `d := time.Since(state.dispatchStart)`, then fans out.
  - `errorHandler` fans out `success = false, d = p2cFailurePenalty`.
  - The old direct `RecordLatency` call becomes unexported `latencyObserver`,
    exposed to `main` through `NewLatencyObserver() RoundTripObserver`. It
    ignores `success` because the duration it receives already encodes the
    failure penalty on the error path — preserving the pre-fan-out behavior
    exactly (real duration on a 5xx that reached the backend, fixed penalty on
    a transport failure).
- `cmd/l7LoadBalancer/main.go`: new `newHandler(reg, sel)` helper constructs
  the proxy and registers `proxy.NewLatencyObserver()` before the server
  starts; `main` uses it as the `http.Server.Handler`. Doc comments note that
  Sprint 3's other two observers register in the same place as they land.
- `internal/proxy/proxy_test.go`:
  - `spyObserver` records every invocation and optionally delegates to an
    `inner` observer, so an observer whose side effect is not countable (the
    latency adapter's EWMA write) can still have its call count asserted.
  - Three new tests, each registering the latency adapter (wrapped) plus a
    plain spy and asserting **count** (`require.Len(..., 1)`):
    `...OnceOnSuccess` (2xx, `success=true`, non-zero duration),
    `...OnceOn5xx` (5xx response, `modifyResponse` path, `success=false`),
    `...OnceOnConnectionRefused` (`errorHandler` path, `success=false`,
    `d == p2cFailurePenalty`).
  - The two existing latency-recording tests now register
    `NewLatencyObserver()`, keeping the same assertions/outcomes.

### Decisions

- **`main.go` registers the latency adapter, following ADR-0011 literally.**
  The slice starts empty in `New`; the composition root wires all three
  observers. The cost is that `New()`-only callers no longer record latency,
  which is why the two existing latency tests were updated to register it.
  The alternative (auto-register inside `New`) was rejected because both the
  ADR and the ticket say `main.go` registers it, and a single composition root
  is the more defensible wiring story for the two observers S3.T2/T3 will add.
- **`NewLatencyObserver()` constructor over an exported adapter type.** It
  returns the `RoundTripObserver` interface and keeps `latencyObserver`
  unexported, matching the repo's `NewX` constructor style (`NewRoundRobin`,
  `NewRegistry`, `NewFromConfig`).
- **A wrapping recorder instead of a second bespoke counter.** One
  `spyObserver` type with an optional `inner` covers both a plain spy and a
  counted latency adapter, so the "exactly once" assertion is uniform.
- **The latency adapter ignores `success`.** Preserving behavior was the
  ticket's explicit requirement, and the failure penalty is already carried in
  `d`; having the adapter branch on `success` would smuggle policy back into a
  dumb adapter.
